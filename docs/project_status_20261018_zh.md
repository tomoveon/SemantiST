## 一、主线

**一句话**：PLC 程序被重编译到宿主机上 fuzz、并以崩溃为判据时，判据在两个方向上都不可靠。宿主机上的崩溃，不能证明原生 PLC 上存在对应缺陷；原生 PLC 上的控制错误，也可能根本不崩溃。

**核心研究问题**：

> 在固定的目标平台语义下，如何区分有意的模运算，与跨扫描周期改变控制决策的数值错误，并给出能在原生平台上重放的证据？

**两个方向的证据**：

| 方向 | 证据 | 状态 |
| --- | --- | --- |
| 崩溃不能证明原生缺陷 | 上周主实验在 OSCAT 上的崩溃，按（工具，目标）统计约 80% 是伪影：RuSTy 标准库 panic、时间类型语义差异、方言转换错误、我们自己的 harness 错误等 | 按独立根因粗算约三分之二；尚未在 CODESYS 上确认 |
| 原生控制错误可能不崩溃 | 在 CODESYS Control Win V3 x64 上手工观察到：INC 的 `MOD 0` 静默返回 0，调用方循环不退出，最终看门狗停机；REAL_TO_STRF 输出 `--695…` 而不崩溃 | 只是存在性的例子；普遍程度要靠实验测量 |

**结论分三层**，只有第三层能称为“有害”：

| 层次 | 含义 |
| --- | --- |
| 1 | 发生了违例（回绕、截断、除零等） |
| 2 | 在规定的参考语义下，该违例造成了输出或分支偏离 |
| 3 | 违反了契约或控制性质，或经原生平台独立确认 |

**可以尝试主张的创新点**（都待原型验证）：

- 两份执行按类型关系比较。例如时钟回绕后，实际值和参考值模 2^w 相等即视为一致，使有意的模差写法不被误报（OSCAT 三库中有 75 个 POU 使用这种写法）。
- 判据绑定目标平台语义：中间结果按寄存器宽度计算、除零行为、TIME 位宽。
- 以扫描周期为单位的干预重放：只纠正某一次违例再重放，判断哪一次违例造成了后果。
- 在原生运行时上重放确认。

**明确不主张的**：

- 只报告传播到敏感位置的违例：IntFlow（ACSAC'14）的 Sensitive Operations 模式已经做过。
- 跨迭代的误差累积：Herbgrind（PLDI'18）的 PID 控制器案例已经分析过。
- 与高精度或参考语义对照：已有前作。

**第一版范围**：确定性、单任务、不含指针和原始内存操作的数值类 FUNCTION/FB。空间内存错误（越界读写）需要另一套证据，不进主线。

**投稿路线**：

- 判据验证通过，并有跨项目的真实缺陷和完整的安全证据链：NDSS 或 USENIX Security。
- 判据有效，但真实影响不足：CCF-B，首选 DSN，其次 ACSAC、RAID。
- 判据验证失败：收缩为“保真度测量＋平台校准”投 CCF-B，同时启动 online change 的可行性验证。online change 本身留作第二篇。

### 3. 验证

- **测试**：Rust 测试 79 + 2 + 6 全部通过，新增的 Python 单测全部通过。全量 Python 测试中仍有 15 个修改前就失败的用例，属于实验验收逻辑，与本次改动无关，尚未处理。
- **镜像**：在本机完整重建失败，原因是构建容器连不上主机代理。改为在上周的实验镜像上只更新源码并重新编译；从那版到现在，Dockerfile、依赖锁和 RuSTy 构建脚本都没有变化，工具链完全相同。新镜像为 `localhost/semantist:exp-94ae1be…`。正式实验仍应按服务器操作手册完整构建。
- **第一轮 smoke**（三工具，3 个目标，各 20 秒）：9 个 run 全部有效。修复重放后，崩溃全部被确认，分类正确：bf_mcpy_1 上 AFL++ 和 SemantiST 都是目标缺陷，CHARNAME 上两者都是工具链 panic。结果在 `artifacts/experiments/smoke_p0_20261018/`。
- **第二轮 P0 验证**（SemantiST，16 个目标，各 60 秒）：

| 目标 | 上周主实验 | 现在 |
| --- | --- | --- |
| 8 个曾有布局错误的功能块（CTRL_PI、CTRL_PID、DRIVER_1、FLOW_CONTROL、FLOW_METER、INTERLOCK、PWM_DC、RMP_B） | 5 次全部无效，启动即崩溃，1–4 exec/s | 全部有效，35–199 exec/s |
| chemical_oobr_1、anaerobic_oobr_1、smart_oobr_1 | 崩溃落在 harness 自己的存储上 | 崩溃落在目标中注入的 memmove/bitcpy 越界上，重放确认为目标缺陷 |
| aircraft_oobw_4 | 同上，是 harness 造成的假崩溃 | 60 秒内未找到注入的缺陷 |
| FINDB_NUM、FINDB_NONUM | 方言转换引起的栈溢出 | 不再崩溃 |
| INC（对照组） | `MOD 0` | 0.26 秒找到，重放确认为目标缺陷 |

16 个目标的重放中，没有一条被判为 harness 错误。结果在 `artifacts/experiments/p0_verify_semantist_20261018/`。

**三个说明后续工作必要性的现象**：

- **FILTER_I**：输入已是合法整数 `T=1`。但 RuSTy 中 TIME 以纳秒为单位，1 ns 换算后为 0，于是除零；CODESYS 没有亚毫秒的 TIME，等价输入是 `T#0ms`。算不算真缺陷取决于平台语义，需要校准。
- **RMP_B**：在线运行时报告了一次 FPE，重放没能复现，因为结果依赖宿主机真实时钟的流逝。需要虚拟时钟。
- **CHARNAME**：SemantiST 用 BYTE 值 255 也触发了 RuSTy 的 UTF-8 panic。评审中“类型化输入天然避开这类伪影”的说法不成立，需要修正。

## 四、接下来的工作

### 阶段 0 剩余部分（本周）

1. **CODESYS 校准包**：最小 ST 程序加记录表。覆盖中间结果宽度、DIV/MOD 除零、REAL_TO_DINT 越界、TIME 回绕与 T_PLC_MS、STRING 编码、LEFT/MID 边界，并把 FILTER_I、RMP_B 两例放进去。
2. **RQ1 按独立根因重新统计**：用修复后的重放处理上周 AFL++ 的崩溃。上周 SemantiST 的数据用的是有缺陷的 harness，单列处理。区分已确认、无法复现和待定。
3. **开发集真值**：把普查 CSV 和 7 个已知问题整理成机器可读格式，并标明来源是人工审计。

### 阶段 1（约 2 周）：平台校准

在固定配置（CODESYS V3.5 SP21 Patch 3、Control Win V3 x64、oscat_basic 3.3.5.0）上，对每个条目做 CODESYS 与 RuSTy 的差分测试。同时实现虚拟时钟，并按校准结果修改溢出谓词。

### 阶段 2（2–3 周）：判据验证（生死线）

- 准备 10–20 个正负例，覆盖：正常模回绕、有害回绕、行为等价的两种写法、状态被覆盖、多次违例互相干扰、寄存器宽度造成的差异。
- 不改编译器。每个例子手写参考版本，配一个小驱动，做逐周期的关系比较和干预重放。
- 判据：对正常回绕和等价写法不误报，多次违例时归因正确。做不到就停下重新考虑方向，不进入扩展阶段。

### 阶段 3（约 2 周）：应用级案例

把一个候选问题放进有明确控制性质的真实 PROGRAM，走通完整的证据链：攻击者能影响的输入 → 满足约束的扫描历史 → 原生平台上的错误行为 → 被违反的控制性质。

### 阶段 4（3–4 周）：正式评测

- 冻结规则，在留出集和外部项目上运行；
- 比较“生成器 × 判定器”的组合，所有工具生成的测试序列交给同一个判定器；
- 消融实验。
