## 一、主线

做一个面向 PLC 控制程序的缺陷检测工具：找出不崩溃、但悄悄算错并因此让控制出错的数值缺陷，排除故意这样写的情况，并在真实 PLC 上确认。

我们改的是"什么样的运行算 bug"这个判据，不是把 ST 跑起来的执行器。平台之间的差异写成一张可测量的平台参数表，作为工具的输入，本身不是研究对象。详见[研究方向](research_direction_zh.md)。

### 3. 验证

- **测试**：Rust 测试 79 + 2 + 6 全部通过，新增的 Python 单测全部通过。全量 Python 测试中仍有 15 个修改前就失败的用例，属于实验验收逻辑，与本次改动无关，尚未处理。
- **镜像**：在本机完整重建失败，原因是构建容器连不上主机代理。改为在上周的实验镜像上只更新源码并重新编译；从那版到现在，Dockerfile、依赖锁和 RuSTy 构建脚本都没有变化，工具链完全相同。新镜像为 `localhost/semantist:exp-94ae1be…`。正式实验仍应按服务器操作手册完整构建。
- **第一轮 smoke**（三工具，3 个目标，各 20 秒）：9 个 run 全部有效。修复重放后，崩溃全部被确认，分类正确：bf_mcpy_1 上 AFL++ 和 SemantiST 都是目标缺陷，CHARNAME 上两者都是工具链 panic。结果在 `artifacts/experiments/smoke_p0_20261018/`。
- **第二轮 P0 验证**（SemantiST，16 个目标，各 60 秒）：

| 目标 | 上周主实验 | 现在 |
| --- | --- | --- |
| 8 个曾有布局错误的功能块（CTRL_PI、CTRL_PID、DRIVER_1、FLOW_CONTROL、FLOW_METER、INTERLOCK、PWM_DC、RMP_B） | 5 次全部无效，启动即崩溃，1–4 exec/s | 全部有效，35–199 exec/s |
| chemical_oobr_1、anaerobic_oobr_1、smart_oobr_1 | 崩溃落在 harness 自己的存储上 | 崩溃落在目标中注入的 memmove/bitcpy 越界上，重放确认为目标缺陷 |
| aircraft_oobw_4 | 同上，是 harness 造成的假崩溃 | 60 秒内未找到注入的缺陷 |
| FINDB_NUM、FINDB_NONUM | 方言转换引起的栈溢出 | 不再崩溃 |
| INC（对照组） | `MOD 0` | 0.26 秒找到，重放确认为目标缺陷 |

16 个目标的重放中，没有一条被判为 harness 错误。结果在 `artifacts/experiments/p0_verify_semantist_20261018/`。

**三个说明后续工作必要性的现象**：

- **FILTER_I**：输入已是合法整数 `T=1`。但 RuSTy 中 TIME 以纳秒为单位，1 ns 换算后为 0，于是除零；CODESYS 没有亚毫秒的 TIME，等价输入是 `T#0ms`。算不算真缺陷取决于平台语义，需要校准。
- **RMP_B**：在线运行时报告了一次 FPE，重放没能复现，因为结果依赖宿主机真实时钟的流逝。需要虚拟时钟。
- **CHARNAME**：SemantiST 用 BYTE 值 255 也触发了 RuSTy 的 UTF-8 panic。评审中“类型化输入天然避开这类伪影”的说法不成立，需要修正。
