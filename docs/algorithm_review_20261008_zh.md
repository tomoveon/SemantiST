**实现的实际算法形态**

1. 从编译器 AST/类型信息提取 STG，记录控制边、数据依赖、持久状态与危险操作。
2. 为违规终点和探索目标枚举有限条候选路径，沿途设置 guide。
3. 使用类型边界、常量与短周期模式生成有限初始种子。
4. 以 `gain / (1 + effort) × exp(-0.25 × failures)` 排序任务；effort 是控制、数据、状态、时间、危险操作五类启发式量之和。
5. 以概率混合语义任务调度和普通队列，再混合定向变异与结构化随机变异。
6. 根据执行反馈更新覆盖、种子画像与任务状态。

目前应称为“ST 语义引导的灰盒模糊测试”，其中多周期变异主要是依赖字段引导和序列结构操作，尚不等于对完整状态转移链求解。

**优势：源码确实具备的基础**

1. **语义事实来自编译器。** 类型、变量角色、控制结果、状态传递和危险操作不是只靠源码字符串匹配。`compiler/stg/src/extract.rs` 的依赖提取、`compiler/stg/src/instrumentation.rs` 的 runtime ID 映射为可解释引导提供了基础。但这些摘要仍有 conservative/opaque 情况，不是完整语义证明。
2. **将危险操作“到达”与“违规”区分。** `hazard_reach` 可以作为中间路标，只有 exact 的违规探针进入语义 objective。这比把经过危险语句直接算漏洞更合理。此处 exact 表示建模/探针判定，不等于每一个整数溢出都具有安全影响。
3. **结构化输入和 IEC 类型相关变异。** 保持 `NAME,TYPE,VALUE` schema；提供整数、浮点、日期时间等边界值，部分分母表达式可以沿局部定义反向调整。初始生成有数量上限，避免无限离线枚举。预期可以减少无效输入，但收益大小需要测量。
4. **多周期序列作为输入对象。** harness 在一次输入内部保留 FB 实例状态，变异支持前缀、末周期、复制、插入、删除等操作；保存完整输入序列有利于重放跨周期行为。
5. **保留探索和消融接口。** 语义任务选择不是绝对贪心；缓存 top-k 种子、失败衰减和普通队列回退有工程价值。当前还不能据此推导最佳调度比例或性能优势。

这些是继续工作的理由。最有潜力的贡献在“利用 ST 语义缩小跨周期危险状态的搜索空间”，需要后续用机制实验证明这一点。

**最终实验前应修复的五项实现缺陷**

**S. 多字段初始种子的周期顺序与 harness 不一致（高优先级）。**

位置：`fuzzer/corpus/generation.rs:614`；`compiler/harness/generator.py:728`、`:738`；`fuzzer/engine/src/mutations.rs:1341`。

初始种子按“字段优先、周期其次”输出。两个字段、两个周期的实际文本顺序是 `0.X、1.X、0.Y、1.Y`。harness 则逐行解析，每遇到 cycle ID 变化就执行上一周期，末尾再执行一次。因此该文本按 harness 合同执行四次扫描，而设计上应是 `0.X、0.Y、1.X、1.Y` 的两次扫描。mutator 解析后又按周期分组，进一步造成初始种子与变异输入的解释差异。

诊断直接调用现有 Rust 序列化函数，确认输出编号 `[0,1,0,1]`，再按实际 harness 的周期切换规则验证为四段；本用例没有另行编译一个真实 FB 进行端到端运行。这是可由双方代码直接确认的合同不一致。

修复要求：统一初始生成与变异的序列表示，先共享配置，再逐周期输出该周期全部字段；harness 可增加编号回退/重复分组的校验。验收不能只检查是否包含 `0.X` 和 `1.X`，而应检查实际调用次数、每次完整输入及前后状态。

**A. 当前种子的进度和全局覆盖混用（高优先级）。**

位置：`fuzzer/semantic/runtime.rs:563`、`:704`、`:905`、`:462`。

- 排名阶段使用最佳种子计算路径和 guide。
- 选择其他种子时沿用上述路径和 guide，没有按实际种子重算。
- 推进时 `active_covered_targets()` 又把全局覆盖并入当前种子覆盖；`record_coverage()` 依据全局集合给当前任务记成功。

两个反例均已复现：最佳种子走过 a、b，探索选择一个没走过它们的种子后，仍直接指导终点 v；另一个反例中，a、b 仅在全局覆盖集合，当前执行只命中 unrelated，guide 却从 a 推进到 v，并记录成功。

这会让“当前种子离目标有多远”的估计失真。多扫描周期场景尤其敏感：不同输入、不同周期的事件不能拼成同一条已满足的状态路径。

修复要求：全局覆盖用于全局新颖性和终点去重；当前 guide、剩余义务和成功归因由当前种子/当前执行证据决定。更换 seed 后重算路径及 guide。最低验收是上述两种情形均不能跳过 a；跨周期义务还应保留顺序，而非只比较集合成员。

**B. 发现违规后跳过语义反馈（高优先级）。**

位置：`fuzzer/engine/src/main.rs:110`、`fuzzer/semantic/observers.rs:51`、`:293`。

项目实际依赖 LibAFL 0.15.4：`StdFuzzer::check_results()` 先调用 objective，仅当不是 solution 时才调用普通 feedback。当前语义覆盖和任务状态更新放在普通 feedback，exact violation 放在 objective。

反例：两个不同内容、正常退出的输入命中同一个违规探针，两次均返回 Solution，但运行时 `covered_target_ids` 中仍没有该违规终点。任务完成信息和普通语义覆盖日志因此可能漏记已发现目标；同一目标的多个不同输入也会持续进入 solution 路径。不是说漏洞输入完全丢失，它们仍被当作 solution 保存。

修复要求：每次执行的语义证据采集必须独立于最终 corpus/solution 分类；保证发现违规时也更新目标完成和本次执行元数据。按稳定目标/诊断类别管理重复候选；根因级 unique bug 仍需另外分析。确认正常输入和违规输入交替执行时，周期轨迹的窗口也不会串到下一输入。

上游调用顺序依据：[LibAFL 0.15.4 源码](https://raw.githubusercontent.com/AFLplusplus/LibAFL/0.15.4/crates/libafl/src/fuzzer/mod.rs)。本次也核对了容器中实际安装的 crate 源码并调用其真实 `check_results()` 进行诊断。

**C. 整数严格比较生成错误边界（高优先级、修复范围较小）。**

位置：`fuzzer/engine/src/mutations.rs:524`、`:550`、`:678`。

比较目标采用浮点的相对步长，例如阈值 10 的步长为 0.1；写回整数时再 round。已复现：希望满足 `X > 10`、`X < 10`、`X <> 10`，三个变异都报告完成，但输出仍是 `X=10`。

修复要求：整数按实际 IEC 位宽、符号和离散边界生成，例如可表示时分别得到 11、9、9 或 11；浮点按可表示相邻值处理；大整数避免经过 f64。返回值应区分“真的改变输入”“满足局部目标”“不支持/不可满足”，避免无效定向变异压制 fallback。测试还应包含上下界、负数、ULINT/LINT 和复合条件。

这不意味着整个 fuzzer 永远过不了这些条件，普通变异仍可能命中；问题在于被宣称为定向的步骤无法完成非常基本的目标。

**D. 普通队列探索仍被计入旧语义任务（高优先级）。**

位置：`fuzzer/scheduler/engine.rs:446`、`:458`；`fuzzer/stages/semantic_budget.rs:23`、`:134`。

队列回退只清空 `TargetContext`，没有清空/暂停 runtime 的 active task 和 guide；预算阶段却从 runtime 读取 guide。已复现：变异上下文为空，但旧 guide 仍存在，随后 25 次执行被记到旧 guide。

这会污染失败衰减和任务延后，导致无法清楚解释调度消融结果。还应审视多个任务共享 guide 时的预算归因：目前按 guide 累计，但失败作用于当前任务。

修复要求：显式记录本轮调度来源及 task/seed/guide；普通探索更新全局发现，但不消耗旧定向任务预算。预算应归属于实际执行上下文，状态切换测试覆盖共享 guide、queue fallback 和任务切换。

**如果最终实验包含跨扫描周期能力，还必须处理的两项限制**

**E. 默认正式实验未向调度器提供周期/状态证据。**

位置：`experiments/comparison/adapters/semantist.py:228`，`experiments/comparison/run_full_comparison.py:98`；`fuzzer/semantic/observers.rs:128`、`:205`、`:231`；`fuzzer/semantic/runtime.rs:1007`。

默认 adapter 提供语义汇总日志，但没有设置 semantic runtime cycle trace；FB state trace 默认为关闭。当前共享内存 map 只有静态 target 的计数，observer 依赖另外的轨迹文件获得周期和状态签名。

诊断中，两周期输入且 target counter 为 2，普通目标能被覆盖，但 `cycle_ids` 和 `state_signatures` 仍为空。输入里写了 `0.X`、`1.X` 不构成“实际执行到了哪些状态”的证据。因而状态成本项无法随状态进展变化，时间成本项也缺少实际周期信息。多周期执行本身仍然存在，缺失的是相应反馈。

开启 trace 后还存在画像问题：`last_state_signatures` 只保留全局首次出现的签名，不能完整描述当前种子走过的状态。同样的有效状态被后来的种子走过时，其画像可能没有这些信息。

修复要求：把“本次执行观察到的状态”与“全局新增状态”分开保存；提供不依赖调试日志开关的轻量反馈，优先共享内存中的周期事件/状态摘要。状态建议按目标相关持久变量投影或抽象，避免一个连续计数器每增一次就无限增加语料。仅临时开启逐事件文件日志可以调试，但不宜未经性能测量就作为最终高吞吐方案。

最低验收：默认实验配置下能区分“相同静态边、不同相关状态进展”的输入；重复已见状态也能准确构建当前 seed profile；序列内事件有可解释的周期和顺序。

**F. 序列增长硬编码为 64 个周期。**

位置：`fuzzer/engine/src/mutations.rs:1484`、`:1499`、`:1567`、`:1600`；`fuzzer/corpus/generation.rs:588`；`fuzzer/semantic/planning.py:887`。

前缀增长、clone、insert、cycle hint 均限制在 64；初始生成的编号周期通常最多 8（实际执行次数还受问题 S 的排序错误影响）；planner 的 temporal requirement 统一给出最低 2 周期，未从计数器/条件推导真正到达深度。诊断请求 100 周期，最终仍为 64，后续增长函数均不能突破。

因此，从短种子出发无法依靠这些增长操作探索需要第 65 周期以后才触发的状态链。已有超过 64 周期的外部种子不属于这个结论；也不是说 harness 无法运行更长输入。仅提高 harness 的 `SEMANTIST_FB_MAX_CYCLES` 不会取消 mutator 的上限。

修复要求：明确并统一生成、变异、执行的周期配置；根据进度以如 8/16/32/64/128/256 的阶段扩大 horizon，同时限制执行时间和无进展成本。至少增加需要超过 64 周期、且相关计数器不能作为输入直接改写的合成目标。它是修复边界的建议验收目标，本次尚未执行该端到端实验。

ICSQuartz 原论文已经讨论固定扫描深度可能漏掉更深漏洞，并提出自适应扫描；因此“支持多个周期”本身不足以构成差异化。[ICSQuartz，NDSS 2025，IV-A](https://www.ndss-symposium.org/wp-content/uploads/2025-795-paper.pdf)

**算法上的进一步劣势：应披露，按目标选择增强，不必都在本轮重写**

1. **effort 主要度量结构数量，不是实际目标距离。** `runtime.rs:984` 的数据成本依赖 waypoint overlap，状态成本主要检查是否有签名，时间成本按周期数扣减。计数器从 1 进到 99、目标需要 100 时，只要静态覆盖相同，当前设计不一定能识别靠近目标。可以加入目标相关分支距离、状态谓词进展、实际执行成本，再做消融验证，不能先验声称等权加和最优。
2. **状态引导尚未解完整 transfer 链。** `mutations.rs:1465` 从 transfer 读取字段集合，随机选一个非末周期改变输入。这有价值，但没有把每个周期对应的守卫、写入和后继状态一起求解；修改前缀后也没有保证已满足的前置条件仍成立。先保护有效前缀，再考虑小范围有界求解或比较反馈，比立刻引入完整符号执行更可控。
3. **不同路径的定义可能混合。** planner 将候选路径的 edge ID 合并后按 ID 排序（`planning.py:793`、`:850`），runtime context 又把所有 transfer 赋值按变量短名收集成一个 map（`observers.rs:512`）。对同名多次赋值、不同分支定义、循环和 FB 实例，这不足以表示到达当前点的定义。应至少按选定路径和程序顺序处理，并保留完整符号身份；确实无法解析时保守降级。这里是源码风险判断，尚未新增完整 ST 目标进行端到端量化。
4. **路径输出有限，不代表搜索开销严格有界。** `bounded_paths()` 最多输出 8/4 条简单路径，但搜索队列没有独立 expansion/time budget。复杂多分支图上可能仍产生大量中间状态，有限路径还可能遗漏有价值的长路径。可增加展开上限、截断信息和按需路径补充。
5. **缺少带数值意义的冷却/重试。** 连续 3 次失败后延期，只有全局新语义覆盖才重新激活（`runtime.rs:501`）。若只有状态改善或新增 seed、没有新静态 target，延期任务可能长期无法重试。可加入有界冷却和与任务有关的新状态/种子触发。
6. **性能成本尚未被单独评估。** 默认每次普通反馈有 target hit 都构造并追加 JSON（`observers.rs:297`、`io.rs:13`）；`ContentHashInputFilter` 对所有尝试输入保存字符串哈希且无淘汰（`observers.rs:634`）。前者有热路径 I/O，后者内存随不同输入数增长。不能据此编造减速比例，但最终实验前应测吞吐、RSS、日志增长，优先批量/增量日志和有界去重。
7. **实验对象边界应清楚。** 当前基础是重新编译 ST 程序和自建 harness，函数块每个测试输入从构造状态开始，在输入内部运行序列。它不自动等价于厂商 PLC runtime、真实定时器、任务调度、物理过程或设备故障模型。对过程安全的主张，需要相应环境模型和安全属性 oracle；仅有 edge coverage、溢出或非崩溃执行不够。当前无需为了软件漏洞实验引入完整物理仿真，但必须准确限定结论。

**建议的执行顺序与冻结条件**

先修 S/A/B/C/D，添加失败先行的正式回归测试；随后完成 E 和周期上限可配置。如果本批次主要比较跨周期能力，同时完成 F 的长序列验收。不要先花数天跑全量、之后再修改这些核心机制。

完成后做少量机制实验再冻结代码：多字段两周期的真实扫描次序；简单严格比较；两条互斥路径/两个不同 seed；普通队列与语义任务交替；正常执行的语义违规；相同边不同状态；超过 64 周期的触发链。检查定向目标命中率、前缀保持率、状态反馈入库率、任务预算归因，同时记录吞吐和内存。

通过这些检查后，固定当前源码提交、编译器/镜像、参数与种子集，再跑主实验和既有消融。所有工具的 wall time、CPU 和执行模型需清楚记录；若比较搜索效率，也应辅助报告执行次数和扫描周期工作量。消融需要证明的是某机制产生了有效引导，而不仅是开关前后得到不同结果。

本次结论支持继续完善现有设计；没有证据要求推倒重写，也没有证据支持现在直接宣称算法已达到最终实验所需的可靠程度。
