# 研究方向

2026-10-18

本文是宏观说明：我们要做一个什么样的工具、为什么要做、和已有工作是什么关系、可能有哪些贡献。怎样一步步做完，见[计划书](research_plan_zh.md)；详细论证和文献对比，见[综合建议](improvement/综合建议（最优方向）.md)。

## 一句话

在 SemantiST 的基础上，做一个面向 PLC 控制程序的缺陷检测工具：自动找出**不崩溃、但悄悄算错，并因此让控制出错**的数值缺陷，排除故意这样写的情况，并给出能在真实 PLC 上复现的证据。

## 1. 问题

PLC 程序出了 bug，真正的后果是控制出错：报警该响不响、阀门开错、计数不对、步骤卡住。而在真实 PLC 上，数值错误通常不会让程序崩溃：

- 整数溢出，直接回绕成另一个数；
- 运算结果在赋值时被截断；
- REAL 转整数越界，得到一个不相干的值；
- 在一些目标上，除零静默返回 0。

程序照常运行，只是值算错了。错的值可能在若干个扫描周期之后，才影响到输出。

现有面向控制程序的 fuzzer 沿用 C 程序的做法：程序崩溃才算发现 bug。对控制程序来说，这个判据在两个方向上都不合适：

- **漏报。** 上面这些错误，不管用哪种方式执行都不崩溃，靠崩溃判断 bug 的工具发现不了。
- **误报。** 把 ST 翻译到宿主机上执行时，会出现真实 PLC 上没有的崩溃，例如翻译工具链自身的 panic，或数据类型的语义不同。

目前的证据都是存在性的：

- 在 CODESYS Control Win V3 x64 上，OSCAT 的 INC 遇到 `MOD 0` 静默返回 0，调用方的循环因此不退出，最终看门狗停机；`REAL_TO_STRF(-3599.0, 6, '.')` 输出 `--695.966720`，也不崩溃。
- 上周的对比实验中，三个工具在 OSCAT 上报告的崩溃，按独立根因粗算约三分之二来自宿主环境，还没有在 CODESYS 上确认。三个工具都用 RuSTy 编译 ST，所以这个数字只代表基于 RuSTy 的流程。

这类错误有多普遍，要靠后面的实验来测量。

## 2. 定位

工控领域的 fuzz 按对象大致分为两类：

| 对象 | 例子 | 崩溃是否是合适的判据 |
| --- | --- | --- |
| 固件、运行时、通信协议 | 对 PLC 运行时或协议栈做二进制 fuzz | 合适。这些是用 C 写的系统代码，崩溃本身就是 bug |
| 控制程序（用户编写的 ST 逻辑） | ICSQuartz 等 | 不合适，见第 1 节 |

我们只做第二类。

一个 fuzzer 可以拆成两部分：

- **执行器**：让程序在大量输入上跑起来；
- **判据**：判断哪一次运行算是发现了 bug。

已有工作主要在改进执行器：怎样把 ST 跑起来（MATIEC 转成 C、RuSTy 编译到 LLVM IR），怎样处理扫描周期，怎样跑得更快。判据则都是"崩溃即 bug"。**我们改的是判据**：对控制程序来说，什么样的运行算 bug，以及怎样自动判断。执行器只负责产生运行，可以替换。

所以，我们不是在研究 RuSTy 和 CODESYS 的编译差异，也不需要逐个研究 MATIEC 等工具链和真实 PLC 之间的差异。

## 3. 要找的缺陷

一次运行要同时满足下面三条，才作为缺陷候选报告：

1. 某个运算在数学上算错了：溢出回绕、截断、除零、转换越界等；
2. 这个错误改变了程序的输出或控制决策，可能是在几个扫描周期之后；
3. 不是故意的写法。

再经真实 PLC 复现，或确认违反了明确的控制性质，才称为缺陷。

| 写法 | 运算出错了吗 | 输出受影响吗 | 结论 |
| --- | --- | --- | --- |
| 计时：`IF T_PLC_MS() - start >= 500 THEN ...`，期间时钟回绕 | 减法回绕 | 不受影响：按模 2^32 计算的差值仍然正确 | 故意的写法，不报 |
| 累计：`total := total + flow; alarm := total > LIMIT;`，`total` 溢出变成负数 | 加法回绕 | 报警该响不响 | 报告 |
| 调用 `INC(X, D, M := -1)` | `MOD 0` | 在 CODESYS 上返回 0，调用方的循环不退出 | 报告 |

第一行的写法，在 OSCAT 三个库中有 75 个 POU 使用。如果只看"有没有溢出"，这些全会被误报。区分故意和有害，是这个工具要解决的核心问题。

注：第一行在 x64 目标上是否真的成立，取决于中间结果按多少位计算，校准用例 410 正在测。这也说明判定必须绑定目标平台。

## 4. 工具是什么样的

**输入**

- ST 程序：FUNCTION、FUNCTION_BLOCK，或包含它们的 PROGRAM；
- 目标 PLC 的平台参数表（第 5 节）。

**输出**：每个缺陷一份报告，包括：

- 触发输入：逐扫描周期的输入序列；
- 出错的运算：位置、第几个周期、实际值和正确值；
- 传播过程：错误经过哪些变量，在第几个周期改变了哪个输出；
- 在真实 PLC 上的复现记录。

**工作方式**分三步：

1. **找**：fuzz 生成大量输入序列，把程序引向有风险的运算，并让它出错。现有的 SemantiST 已经基本能做到这一步。
2. **判**：对每个让运算出错的输入，把程序运行两遍来比较：
   - 一遍按目标 PLC 的规则计算，称为平台执行；
   - 一遍让出错的运算取数学上正确的值，称为参考执行。

   输出一致，说明这次出错是故意的或无害的。输出不同，再每次只改正其中某一次出错，重新运行，找出到底是哪一次造成了后果。比较时，像时钟这样本来就按模计算的量，按模相等就算一致。
3. **证**：把输入序列放到真实 PLC 上运行，确认出现同样的错误输出。

## 5. 平台差异怎么处理

不同 PLC 的行为确实不完全一致。这恰好说明不能拿"在某个环境里崩没崩"来定义 bug：缺陷在程序里，平台只决定它表现成什么样。同一个 INC 除零，在 CODESYS 上静默返回 0、导致死循环，在 RuSTy 上直接崩溃，但它是同一个缺陷。

平台之间的差异集中在少数几项：

- 整数运算的中间结果按多少位计算，在哪里截断；
- 除零、除法溢出时，是陷入异常，还是返回某个值；
- REAL 转整数越界时得到什么；
- TIME 等时间类型的位宽、单位和回绕方式；
- 字符串的长度上限和编码，以及函数参数越界时的行为。

我们把这些写成一张平台参数表，作为工具的输入。在"判"这一步，工具在这些运算上按参数表计算，不依赖执行器自身的默认行为。因此：

- **换一种 PLC**，只需换一张参数表，工具本身不用改。很多厂商的 PLC 基于 CODESYS 运行时，大部分条目相同；个别条目（如除零）与硬件有关，所以参数表按"运行时＋硬件"来测量。
- **换一种执行器**，判定结果不受影响。我们计划在 ST 源码层实现这一步，变换后的程序可以交给 RuSTy、MATIEC 或其他 ST 编译器运行。
- **校准用例**（`experiments/calibration/`）的作用，就是在 CODESYS 上测出这张表，同时为"证"这一步准备好环境。它是工具的一项输入，本身不是研究内容。

## 6. 可能的贡献

以下都是当前的设想，需要原型和实验来证实。

1. **问题与定义。** 指出对 PLC 控制程序来说，"崩溃即 bug"在漏报和误报两个方向上都不适用；提出以控制后果为准、分三层的缺陷定义：运算出错 → 输出或决策被改变 → 经真实 PLC 或控制性质确认。
2. **区分故意与有害的判定方法（核心）。** 对比同一程序的平台执行与参考执行：
   - 对本来就按模计算的量按模比较，避免把故意的回绕误报；
   - 以扫描周期为单位做干预重放，在多次出错之间找出真正造成后果的那一次，并给出跨周期的传播过程。
3. **按平台参数化的判定。** 把判定所依赖的平台行为收敛为一张可测量的参数表，并给出测量方法；判定不依赖具体的执行器。
4. **原型与端到端证据。** 包括：
   - 开源原型；
   - 发现的缺陷在真实 PLC（CODESYS）上复现；
   - 在 OSCAT 和未审计过的外部项目上的发现；
   - 至少一个应用级案例，从攻击者能影响的输入一直到违反控制性质。
5. **附带的测量。** 基于 RuSTy 的现有 fuzzer 所报告的崩溃，有多少在真实 PLC 上不成立；它们漏掉了多少静默缺陷。

不主张的部分：

- 只报告影响输出的错误：整数方面 IntFlow（ACSAC'14）、浮点方面 Herbgrind（PLDI'18）已经做过；
- 与高精度执行对照、分析跨迭代的误差累积：Herbgrind 已有；
- 通过比较两次运行的状态差异来隔离因果链：Zeller（FSE'02）是直接前作。

我们的新意要落在 PLC 带来的具体困难上：故意的模运算到处都是；判定依赖目标平台；错误跨扫描周期传播；结论要在真实 PLC 上确认。

## 7. 范围

**第一版做的：**

- 数值类 FUNCTION 和 FUNCTION_BLOCK，即整数、REAL、TIME 运算，不含指针和原始内存操作；
- 确定性、单任务的执行；
- 目标平台：CODESYS V3.5 SP21 Patch 3、Control Win V3 x64、oscat_basic 3.3.5.0。

**不做的：**

- 固件、运行时和通信协议；
- 越界读写等内存错误，这类问题需要另一套证据；
- 编译器之间的差异研究；
- online change，作为备选的第二个方向。

## 8. 主要风险

| 风险 | 后果 | 应对 |
| --- | --- | --- |
| 判定方法分不清故意和有害 | 核心贡献不成立 | 计划的第一阶段就用 10–20 个小例子检验，不通过就停下来重新考虑 |
| 真实库中有害的静默缺陷不多 | 影响力不足 | 扩大到外部项目，或降为投 CCF-B |
| 与前作的区别不够大 | 新颖性受质疑 | 用原型结果说明，PLC 特有的困难确实需要新的机制 |
| 安全意义不足 | 难进安全顶会 | 至少做出一个完整的应用级案例 |

**投稿预期：**

- 判定方法有效，跨项目都有真实缺陷，并有完整的安全证据链：投 NDSS 或 USENIX Security；
- 判定方法有效，但真实影响不足：投 DSN、ACSAC 或 RAID。
