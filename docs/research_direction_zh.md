# 研究方向

本文是宏观说明：我们要做一个什么样的工具、为什么要做、和已有工作是什么关系、可能有哪些贡献。怎样一步步做完，见[计划书](research_plan_zh.md)；方法细节和文献对比的初版，见[综合建议](improvement/综合建议（最优方向）.md)，其中与本文不一致的地方（如第 3.4 节"按关系比较"），以本文为准。

## 一句话

在 SemantiST 的基础上，做一个面向 PLC 控制程序的数值缺陷检测工具：自动找出**不崩溃、但悄悄算错**的运算，判断它**有没有改变控制行为**，并给出能在目标 PLC 上复现的证据；是不是缺陷，再依据明确的性质或规格确认。

写论文时用的精确说法：

> 面向明确的目标平台与受支持的 ST 程序子集，在给定的输入约定、初始状态和观察窗口下，分析数值风险事件对可观察控制行为的影响；以明确的性质确认缺陷，并提供可重复的原生证据，以及与证据强度相称的干预解释。

## 1. 问题

PLC 程序出了 bug，真正的后果是控制出错：报警该响不响、阀门开错、计数不对、步骤卡住。而在真实 PLC 上，数值错误通常不会让程序崩溃：

- 整数溢出，直接回绕成另一个数；
- 运算结果在赋值时被截断；
- REAL 转整数越界，得到一个不相干的值；
- 在一些目标上，除零静默返回 0。

程序照常运行，只是值算错了。错的值可能在若干个扫描周期之后，才影响到输出。

现有面向控制程序的 fuzzer，多数以崩溃或 sanitizer 报错作为判据（第 2 节有更细的对照）。对上面这类错误，这个判据在两个方向上都不合适：

- **漏报。** 这些错误大多不崩溃，也不触发 sanitizer 检查或设备上可见的异常；除非有人恰好为它写了断言，否则发现不了。
- **误报。** 把 ST 翻译到宿主机上执行时，会出现真实 PLC 上没有的崩溃，例如翻译工具链自身的 panic，或数据类型的语义不同。

反过来，如果把"运算出错"本身就当作 bug，又会把大量本来就按模计算的写法报出来（第 3 节）。

目前的证据都是存在性的：

- 在 CODESYS Control Win V3 x64 上，`REAL_TO_STRF(-3599.0, 6, '.')` 输出 `--695.966720`，不崩溃。
- OSCAT 的 INC 遇到 `MOD 0`，在 CODESYS 上静默返回 0，调用方的循环因此不退出，最终看门狗停机；在 RuSTy 上则直接崩溃。不过触发它的 `M := -1` 超出了 INC 的参数约定（M 是计数上限），所以它说明的是同一个问题在不同平台上表现不同，不能直接算作有效输入下的缺陷。
- 上周的对比实验中，三个工具在 OSCAT 上报告的崩溃，按独立根因粗算约三分之二来自宿主环境，还没有在 CODESYS 上确认。三个工具都用 RuSTy 编译 ST，所以这个数字只代表基于 RuSTy 的流程。

这类错误有多普遍、其中有多少真的改变了控制行为，要靠后面的实验来测量。

## 2. 定位

工控领域的 fuzz 按对象大致分为两类：

| 对象 | 例子 | 崩溃或设备故障是否是合适的判据 |
| --- | --- | --- |
| 固件、运行时、厂商指令库、通信协议 | 对 PLC 运行时或协议栈做二进制 fuzz；LogicFuzz（NDSS'26）通过控制程序调用固件中的厂商指令，在真机上监控故障和挂起 | 基本合适。被测的是厂商实现的系统代码，崩溃、挂起本身就是 bug |
| 控制程序（用户编写的 ST 逻辑） | ICSQuartz（NDSS'25）、StructuredFuzzer（Electronics'24）等 | 不够，见第 1 节 |

我们只做第二类。

一个 fuzzer 可以拆成两部分：**执行器**让程序在大量输入上跑起来，**判据**判断哪一次运行算是发现了 bug。在控制程序上，已有的判据大致有三种：

| 判据 | 代表 | 能发现 | 发现不了 |
| --- | --- | --- | --- |
| 崩溃与 sanitizer 报错 | ICSQuartz 等基于 RuSTy 的 fuzzer | 内存错误、会陷入异常的运算 | 不崩溃的错值；宿主上的崩溃在 PLC 上未必成立 |
| 设备上可见的异常 | LogicFuzz：运行日志、状态灯、通信状态 | 故障、挂起、超时 | 设备运行正常、只是值算错的情况；而且需要真机 |
| 人工写的性质断言 | StructuredFuzzer 等 | 违反断言的错值 | 没写断言的地方；每个程序都要有人写性质 |

各工作判据的细节，计划书阶段 1 会通读原文再核实一遍。

我们改的是判据：**不要求为每个程序写性质，自动判断一次不崩溃的数值错误有没有改变控制行为。** 执行器只负责产生运行。

我们不研究编译器之间的差异本身。但判定依赖目标平台实际怎样执行，这一部分必须实测（第 5 节）。第一版只针对一个明确的平台配置；能否低成本地换到其他平台和执行器，是要验证的目标，不是现成的结论。

## 3. 要找什么：结论分三层

工具不推断开发者的意图：一处回绕是不是故意的，属于功能要求，只能由规格或人来确认。工具能做的，是判断它在给定条件下有没有改变控制行为。所以结论分三层：

| 层次 | 含义 | 能说明什么 |
| --- | --- | --- |
| 1 风险事件 | 某个运算发生回绕、截断、信息丢失，或定义域错误（除零、转换越界） | 运算出了界，不说明程序错了 |
| 2 影响候选 | 在规定的参考语义和观察窗口内，这个事件改变了输出、控制决策或终止行为（如循环不退出） | 在这个输入、初始状态和窗口下，事件有可观察的后果 |
| 3 已确认缺陷 | 在明确的适用条件下，违反了接口约定、控制性质或有依据的功能要求 | 是缺陷；安全影响另行判断 |

此外还有几种结论必须如实保留，不能统一当作"无害"：

- **未观察到影响**：只说明在这个输入和窗口内没看到差异；
- **潜伏差异**：状态已经不同，但窗口内还没有影响输出；
- **参考未定义**：例如除零，没有数学上的正确值（第 4 节）；
- **不支持**：用到了第一版范围之外的语义；
- **预算不足**：重放或归因没有做完。

在真实 PLC 上复现，是单独的一项证据，记为已复现、未复现或未验证。复现说明这个行为在目标平台上确实存在，但不说明它是缺陷；一次没复现，也不自动等于误报。

| 写法 | 风险事件 | 窗口内有没有影响 | 结论 |
| --- | --- | --- | --- |
| 计时：`IF T_PLC_MS() - start >= 500 THEN ...`，期间时钟回绕 | 减法回绕 | 没有：参考执行用不回绕的时间，经过时间相同，判断相同 | 未观察到影响，不报 |
| 同上，但两次读数之间经过的时间超过 2^32 ms | 减法回绕 | 有：参考执行得到真实的经过时间，判断不同 | 影响候选 |
| 累计：`total := total + flow; alarm := total > LIMIT;`，`total` 溢出变成负数 | 加法回绕 | 有：报警该响不响 | 影响候选；"超限必须报警"这一性质成立时，确认为缺陷 |
| 调用 `INC(X, D, M := -1)` | `MOD 0` | 参考未定义 | 风险事件；`M = -1` 超出 INC 的参数约定，首先是调用方的问题 |

第一行的写法，在 OSCAT 三个库中有 75 个 POU 使用。如果只看"有没有溢出"，这些都会被报告。它们大多应当不报，但写法相同不代表都没问题，评测时不能直接当作真负例。把"回绕了但不影响行为"和"回绕改变了控制行为"分开，是这个工具要解决的核心问题。

注：第一行在 x64 目标上是否成立，取决于中间结果按多少位计算，校准用例 410 正在测。INC 在 `M := 32767` 这个合法上限上会不会算错（`M + 1` 溢出），同样取决于这一点。所以判定必须绑定目标平台。

## 4. 工具是什么样的

**输入**

- ST 程序：FUNCTION、FUNCTION_BLOCK，或包含它们的 PROGRAM；
- 目标平台配置：开发系统和运行时版本、设备、库版本、检查设置（例如工程里有没有 CheckDivInt 这类隐式检查函数），以及实测的平台参数表（第 5 节）；
- 可选的输入约定：输入的合法范围、初始状态。没有时按类型的全部取值处理，并在结论中注明。

**输出**：每个发现一份报告，包括：

- 结论层次，或第 3 节中的某种不确定结论；
- 触发输入：逐扫描周期的输入序列、时钟和初始状态，以及它们是否满足输入约定；
- 风险事件：位置、所在的调用实例、第几个周期、平台值和参考值（或"参考未定义"）；
- 影响：在第几个周期改变了哪个输出或决策，以及经重放验证的干预集合；
- 原生复现状态；
- 确认依据：违反了哪条性质或规格。没有依据的，保持为影响候选。

**工作方式**分三步：

1. **找**：fuzz 生成大量输入序列，把程序引向有风险的运算，并让它出错。现有的 SemantiST 已经基本能做到这一步。fuzz 时使用按目标平台语义构建的程序，否则某些只在目标平台上可达的行为根本搜不到，事后判定也补不回来。
2. **判**：对每个触发了风险事件的输入，把程序运行两遍：
   - **平台执行**：按目标平台的规则计算；
   - **参考执行**：按事先规定的参考语义计算。参考语义按运算类型分别规定，不笼统地取"数学正确值"：
     - 整数加减乘、隐式窄化、REAL 转整数越界（有限值）：用更宽的整数，保留精确值；
     - 时钟：用不回绕的虚拟时间。正常的计时回绕在参考执行中得到同样的经过时间，所以不会被误报；
     - 显式窄化、位运算、移位：两边都按模计算。这是一条规定，不代表这些运算一定正确，可能因此漏报；
     - 除零、NaN 转整数这类定义域错误：没有正确值可取。改为用几个不同的替代值分别运行；输出随替代值变化，就说明输出依赖一个未定义的结果。

   比较的是输出、控制决策和终止行为，不比较中间变量：状态不同而这三者相同，记为潜伏差异。出现影响时，再做干预重放：只修正其中某些事件，重新运行，找出后果离不开哪些事件。一个后果可能需要几个事件同时出错才会出现，所以结果是一个事件集合；结论只说"在这个参考和干预模型下，经重放验证"，不说找到了根因。
3. **证**：
   - 把输入序列、时钟和初始状态放到真实 PLC 上运行，看是否出现同样的行为；
   - 再对照接口约定、控制性质或功能说明，判断是否构成缺陷。

## 5. 平台差异怎么处理

不同 PLC 的行为确实不完全一致。这恰好说明不能拿"在某个环境里崩没崩"来定义 bug。同一个 INC 除零，在 CODESYS 上静默返回 0、导致死循环，在 RuSTy 上直接崩溃：问题是同一个，表现不同。

判定所依赖的平台行为，集中在少数几项：

- 整数运算的中间结果按多少位计算，在哪里截断；
- 除零、除法溢出时，是陷入异常，还是返回某个值；工程中的隐式检查函数（CheckDivInt、CheckRange 等）会在运算前改变处理；
- REAL 转整数越界时得到什么；
- TIME 等时间类型的位宽、单位和回绕方式；
- 字符串的长度上限和编码，以及函数参数越界时的行为。

所以"运行时＋硬件"不足以标识一个平台。我们记录完整的平台配置（开发系统和运行时版本、设备、库版本、检查设置、STRING 编码），并把上面这些行为实测成一张平台参数表。在"判"这一步，工具在这些运算上按参数表计算，不依赖执行器自身的默认行为。

下面几点是设计目标，需要实验验证，不是已经成立的结论：

- **换平台只换表。** 很多厂商的 PLC 基于 CODESYS 运行时，大部分条目可能相同。但表有实测支撑，不等于覆盖了所有相关的表达式和调用上下文。第一版只承诺一个平台配置；有条件时再测第二张表，作为附加证据。
- **不绑定执行器。** 我们计划在 ST 源码层构建参考执行，变换后的程序原则上可以交给 RuSTy、MATIEC 或其他 ST 编译器。但"变换后仍是 ST"不能证明各编译器下的判定一致，第一版只在 RuSTy 上验证。
- **校准用例**（`experiments/calibration/`）测的是目标平台实际怎样执行，用来产出参数表，并为"证"这一步准备好环境。它说明平台怎样执行，不说明这样执行符合规范。

## 6. 可能的贡献

以下都是当前的设想，需要原型和实验来证实。每一项都写明已有工作做到了什么、我们要新增什么、怎样验证。

| 拟议贡献 | 已有工作做到的 | 我们要新增的 | 怎样验证 |
| --- | --- | --- | --- |
| 1 判据与定义（主要） | 控制程序上已有崩溃与 sanitizer、设备异常监控、人工性质断言三种判据 | 不写逐程序性质，判断静默数值事件有没有改变控制行为；分层给出结论，如实保留不确定的结果 | 判据验证集；在同一组输入上与另外几种判据对比 |
| 2 面向 PLC 的参考语义（核心） | IntFlow 只报流入敏感位置的整数错误；IOC 研究了故意与非故意的整数溢出；Herbgrind 用高精度影子值分析浮点误差的影响，包括跨迭代的累积 | 面向 ST 和扫描周期、按运算类型规定的参考语义：用不回绕的虚拟时钟处理计时回绕，定义域错误用多个替代值运行，全部语义绑定实测的平台配置 | 合法回绕、超出时间跨度、等价改写、定义域错误等用例；75 个模差写法 POU 上的报告情况 |
| 3 干预解释（次要） | Zeller 用 Delta Debugging 在两次运行之间隔离因果链 | 以扫描周期为单位的事件干预：对照的一方是规定的参考语义；处理联合原因、重复事件和干预后事件对不上的情况 | 联合原因、可替代原因、互相抵消、分支改变等用例；小例子上穷举事件子集对照 |
| 4 原型与端到端证据 | ICSQuartz 有原生平台上的验证；LogicFuzz 在真机上测试 | 发现在 CODESYS 上复现，并按性质确认；在未审计过的外部项目上的发现；至少一个从攻击者可影响的输入到违反控制性质的应用级案例 | 原生复现率；确认依据；维护者的确认 |
| 5 附带的测量 | — | 基于 RuSTy 的 fuzzer 报告的崩溃，有多少在 CODESYS 上不成立；崩溃判据漏掉了多少静默问题 | 重放分类与原生复现 |

不主张的部分：

- 扫描周期建模、真机测试、超越崩溃的异常监控本身：ICSQuartz、LogicFuzz 等已有；
- 只报告影响输出的错误：整数方面 IntFlow（ACSAC'14）、浮点方面 Herbgrind（PLDI'18）已经做过；
- 与高精度执行对照、分析跨迭代的误差累积：Herbgrind 已有；
- 通过比较两次运行的状态差异来隔离因果链：Zeller（FSE'02）是直接前作；
- 研究对象在 ST 应用层，这一点本身不构成创新；
- 按平台参数化、不绑定执行器：是设计特性，不作为主要贡献。

我们的新意要落在 PLC 带来的具体困难上：故意的模运算到处都是，判定依赖目标平台，错误跨扫描周期传播，结论要在真实 PLC 上确认。"前作没有展示过"不能代替对新方法有效性的验证。

## 7. 范围

**第一版做的：**

- 数值类 FUNCTION 和 FUNCTION_BLOCK：整数运算、窄化、比较，以及少量已校准的时间运算；除零等定义域错误单独处理；
- 确定性、单任务的执行；
- 可观察的后果：输出、指定位置的控制决策、终止行为（循环不退出、超出周期预算）；
- 目标平台配置：CODESYS V3.5 SP21 Patch 3、Control Win V3 x64、oscat_basic 3.3.5.0，检查设置以校准时的工程为准。

**是否加入，看原型结果：**

- 一般的浮点精度问题；
- 字符串函数的语义；
- 第二个平台或执行器。

**不做的：**

- 固件、运行时和通信协议；
- 指针和原始内存操作，以及越界读写等内存错误，这类问题需要另一套证据；
- 编译器之间的差异研究；
- online change，作为备选的第二个方向。

## 8. 主要风险

| 风险 | 后果 | 应对 |
| --- | --- | --- |
| 参考语义分不清"回绕但不影响行为"和"回绕改变了行为" | 核心贡献不成立 | 第一阶段先定语义范围表和判据验证集，预期结论在设计规则之前固定，并保留独立变体；不通过就修改定义或收缩范围 |
| 非时钟的故意模运算（校验和、序号、哈希）没有"不回绕的真值" | 只能按规定两边都按模计算，可能漏报 | 作为已知局限，报告这类运算所占的比例；判断不了的标为不确定 |
| 搜索阶段与判定阶段的语义不一致 | 只在目标平台上可达的行为搜不到 | fuzz 使用平台语义构建，并单独评估差异的影响 |
| 判据验证集只能证明内部一致 | 不能说明判据通用 | 加入独立变体和 OSCAT 中的真实写法；在留出集和外部项目上评测 |
| 真实库中有害的静默缺陷不多 | 影响力不足 | 扩大到外部项目，或降为投 CCF-B |
| 与前作的区别不够大 | 新颖性受质疑 | 用原型结果说明，PLC 特有的困难确实需要新的机制 |
| 安全意义不足 | 难进安全顶会 | 至少做出一个完整的应用级案例 |

**投稿预期**：去向依据结果和领域适配决定，下面只是目前的预期。

- 判定方法有效，跨项目都有确认的缺陷，并有完整的安全证据链：NDSS 或 USENIX Security；
- 判定方法有效，但真实影响不足：DSN、ACSAC 或 RAID。

## 附：2026-10-19 修订要点

依据外部评审意见修订。主要改动如下：

| 原来的说法 | 问题 | 现在的说法 |
| --- | --- | --- |
| 输出一致，说明出错是故意的或无害的 | 有限的运行只能说明没观察到差异；是否故意属于功能要求 | 结论分三层，并保留"未观察到影响""潜伏差异"等结果（第 3 节） |
| 参考执行让出错的运算取"数学上正确的值" | `MOD 0`、NaN 转整数没有正确值；各类运算的舍入和范围规则不同 | 按运算类型规定参考语义；定义域错误用多个替代值运行（第 4 节） |
| 时钟派生的量按模相等就算一致 | 模相等的值进入比较后，结果可能不同（评审给出了 8 位时钟的反例） | 模运算在参考语义中处理（不回绕的虚拟时钟），只比较输出、决策和终止行为 |
| 经真实 PLC 复现，或确认违反控制性质，才称为缺陷 | 复现只说明行为真实存在 | 原生复现单列为一项证据；确认缺陷需要性质或规格 |
| 现有控制程序 fuzzer 的判据都是崩溃即 bug；已有工作主要在改进执行器 | LogicFuzz 监控设备异常，StructuredFuzzer 用性质断言 | 按判据类型重新定位（第 2 节） |
| 换平台只换表；换执行器，判定结果不受影响 | 未经验证；"运行时＋硬件"也不足以标识平台 | 降为待验证的设计目标，不作为主要贡献；记录完整的平台配置（第 5 节） |
| 干预重放找出"到底是哪一次"造成了后果 | 后果可能需要几个事件同时出错；Delta Debugging 只保证局部最小；干预后事件可能对不上 | 只给出经重放验证的干预集合，并标明最小性和是否对齐 |
| INC 的 `MOD 0` 作为有害缺陷的例子 | `M = -1` 超出 INC 的参数约定 | 改作同一问题在不同平台上表现不同的例子 |
