# Container extraction (layer 1)

This package turns the collected vendor containers in `rusty_compatibility/`
(ZIP/`.library` archives, PLCopen XML, TwinCAT projects, CODESYS 2.3 binary
libraries, PC WORX CFB packages, SIMATIC AX apax packages, ...) into one ST file
per library or project. It is the extraction that produced
`rusty_compatibility/*/.st文件/`; the scripts were moved here from
`rusty_compatibility/提取脚本/` (removed after the move; the original version is
in Git history at commit `1af6559`).

Only the Python standard library is used. Nothing below `rusty_compatibility/`
is written.

## Running

```bash
python3 -m compiler.intake.extract run --work-dir artifacts/intake/extract
python3 -m compiler.intake.extract compare --work-dir artifacts/intake/extract \
  --output artifacts/intake/extract/comparison.json
```

`run` executes the extractor groups `xml industrial legacy pcworx native other
sysmac` in separate processes (in that order; `pcworx` completes the `legacy`
PC WORX output) and writes:

| Path | Content |
| --- | --- |
| `outputs/<vendor>/.st文件/*.st` | extracted libraries and projects |
| `provenance/<group>.json` | per output file: the original container chains |
| `pou-index.json` | per POU: kind, name, output lines, source marker, original container chain and, when the member is text, the declaration line (`source_line`) or, for binary records, the byte offset (`source_offset`) |
| `raw-inventory.json` | every raw `.library` (also nested in archives) and whether it is ingested |
| `extraction.json` | groups, curation steps, fixed inputs, SHA-256 of every output |
| `logs/` | the extractors' own diagnostic records |

A *container chain* is a path relative to the corpus root followed by
`!member` per nested archive level, for example
`02_CODESYS23/原始库文件/源码/x.zip!dir/y.zip!codesys/IP_CONTROL.EXP`.

## Extraction boundary

The extractors keep the boundary of the original scripts: encrypted
implementations, declarations that cannot be completed from the container, and
storage relations that cannot be represented faithfully (Rockwell alias and
bit-overlay tags, Schneider `ExtractBit`) are not reconstructed. Mixed-language
projects contribute only their ST part. Extraction success says nothing about
RuSTy compatibility; that is decided by the later layers.

`.library` files that start with `23 89 ed 33` (about 8 bits/byte of entropy;
nine distinct files, fifteen occurrences including copies inside other archives)
use an undocumented compressed or encrypted format and are listed in
`raw-inventory.json` under `not_ingested`.

## Differences to the original Windows run

`compare` rewrites the absolute Windows corpus path in legacy headers
(`(* Original library/project: D:\IIOT\projects\rusty兼容层\...`) to the
corpus-relative path and then requires byte equality with every collected file.
The remaining differences of the archived scripts are host effects or manual
steps taken after the original run; they are recorded in `curation.json`, each
with its reason, and replayed by `run`:

* **Name budget and collisions.** The original budget for generated names was
  derived from the absolute output path (Windows MAX_PATH) and collisions were
  detected by a case-insensitive file system. `naming.py` replaces both with a
  fixed budget and a case-insensitive check, so names no longer depend on the
  host or the work directory.
* **Collision suffixes** hash the container chain; on Windows that chain was
  absolute. The collected names are restored by `renames` entries.
* **Manual renames** (`native_oscat_basic_<version>_codesys.st`, ...) and the
  manual merge of the three OSCAT network 1.12 patch POUs into
  `native_oscat_network_112_patch.st` are `renames` and `merges` entries.
* **One header refinement** (`native_Siemens_SCL_Source_Files_Timer.st` names
  the `!Timer` subtree) is a `headers` entry.

Some collected files are not produced by the extractors and are copied as
*fixed inputs* (`fixed_inputs` in `curation.json`):

* `oscat_basic_335.st` in `01_CODESYS3` and `34_OpenPLC_v4_STruCpp`: a
  user-provided whole-library export of CODESYS OSCAT Basic 3.3.5.0.
* `JiecLib_*.st`, `JiecUnit_*.st` in `18_Omron_Sysmac` and `20_KEYENCE_KV`:
  generated by the official Jiecc 8.0.0 macro expander, which is a Windows
  executable. On Windows `--parts jiec --jiecc path/to/jiecc.exe` regenerates
  them; otherwise the collected outputs are used.
